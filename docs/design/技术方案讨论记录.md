# Ontology 技术方案讨论记录

功能方案已整体确认，见《Ontology-多用户方案确认稿-v1.1.md》。技术选型仍需逐项确认，已有技术设计属于建议，不自动视为批准。

## 讨论规则

- 每次只确认一个技术点。
- 提问前，先从使用场景解释原理，解释出现的术语，再比较取舍。
- 使用当前主流且适合现有 Java 后端及 Workbench 生态的技术。
- 各登录入口共享内部用户与业务权限，但浏览器凭证和 Agent 调用凭证可以不同。

## 已确认

T01：用户确认浏览器采用 Ontology Java 后端维护的服务端 Session，浏览器 Cookie 仅携带随机会话编号。两种登录路径均归一到内部用户；本项不同时确认具体实现框架、会话存储、有效期或 Agent 令牌。

T02：用户确认第一版使用现有 PostgreSQL，并由 Spring Session JDBC 保存和管理浏览器会话，不为会话另增 Redis 服务。会话有效期、清理策略和具体依赖版本仍待确认。

T03：用户确认采用 Spring Security 作为 Java 后台的统一安全框架，处理通用认证、会话身份恢复与请求安全；项目权限由业务授权模块实现，Spring Session JDBC 负责会话存储。具体版本、升级及旧接入层迁移另行讨论。

T04：用户确认 Workbench 网页登录采用 OIDC 授权码流程并启用 PKCE，由 Java 后台兑换和验证身份结果，再建立 Ontology 自己的 Session。使用顶层跳转和已登记回调，不向 Ontology 提交 Workbench 密码。

T05：用户确认使用 Spring Security 的 OIDC 验证能力，从已配置且可信的 Workbench JWKS 获取公钥，对 ID Token 验签，并检查 issuer、audience（对应注册 Client ID）、有效期、nonce 及协议要求的其他字段；验证失败不建号、不建立会话。

T06：用户确认由 Ontology 维护独立内部 user_id，项目权限与会话关联该内部用户；本地登录凭据及已验证的 Workbench (iss, sub) 分别关联内部用户。外部身份组合建立数据库唯一约束，不按邮箱自动合并；两种登录方式须按已确认的双重验证流程显式绑定。首次 Workbench 登录按已确认规则创建无既有项目权限的内部账号。具体内部 ID 格式另行确定。

T07：用户确认使用 Spring Security 的 PasswordEncoder，以 Argon2id 执行带随机盐的单向密码哈希；数据库保存编码后的算法标识、参数、盐及哈希结果，不保存明文或可解密密码。密码通过 HTTPS 送达 Java 后端，使用框架验证；保留编码版本及后续升级能力。参数以当前安全基线为起点，在目标环境测量耗时和内存后确定，不直接沿用框架默认值。此项不同时确认密码强度、登录限流、找回密码或会话撤销策略。

T08：用户确认两种网页登录统一采用闲置 30 分钟、单次登录最长 8 小时，任一到期即由 Java 后端拒绝继续使用该会话，重新登录后建立新会话。闲置按服务端收到的有效使用请求计算，纯后台轮询 / 保活不应无限续期；具体请求分类在实施中设计验收。到期前页面提示；仅本地编辑不代表后端收到使用请求。Workbench ID Token 在登录时验证有效期，其 exp 不直接作为已建立的 Ontology 会话到期时间；重新登录可利用仍有效的 Workbench 登录状态，但不承诺免交互或已支持平台强制重新验证。用户同时提出希望有 Refresh Token 自动续期，具体适用链路与是否调整 8 小时边界进入 T09 讨论，尚不视为批准长期免登录。Agent 凭证有效期、会话撤销、敏感操作重新验证及持久登录能力另行讨论。

T09：用户选择 A，确认自动续期不突破 T08 的单次登录 8 小时上限，不增加跨天持久登录。浏览器有效使用请求本身滚动延长闲置期限，无需另发浏览器 Refresh Token；纯后台刷新不抵消闲置限制。上游 Refresh Token 用于换取上游 API 凭证，不构成用户重新交互验证，也不自动延长 Ontology 会话。2026-10-20 再次读取 Workbench 公开 discovery：grant_types_supported 仅声明 authorization_code，scopes_supported 未声明 offline_access；没有证据确认当前已向该客户端开放刷新，不能推断平台绝对不支持。后续若有上游 API 调用需要且平台支持，可由 Java 服务端安全保管并刷新；下游 Agent 刷新能力按独立授权链路及 Workbench 消费方契约讨论。本项确认体验与时长边界，不代表平台刷新能力、刷新凭证参数或具体实现已确认。

T10：用户确认浏览器会话采用服务端作废会话及账号安全版本校验。Java 在每次受保护请求中检查数据库中的内部用户启用状态及 auth_version（安全版本号），与会话建立时保存的版本比较。普通退出仅作废当前会话；退出全部设备、密码重置等账号级撤销增加安全版本并撤销旧会话；账号禁用后两种登录及旧会话均不通过，重新启用也不复活旧会话。安全状态修改与版本更新应在同一事务提交；提交后进行安全校验的新请求按新状态拒绝，不能承诺取消已经通过校验或执行中的请求。会话存储与状态无法读取时拒绝受保护访问。项目成员/角色从项目权限事实源检查，不把移出一个项目等同于禁用整个用户。Agent 授权的撤销范围后续单独确认，不因本项自动扩大浏览器退出的影响范围。

T11：用户确认网页登录启用 Spring Security 标准 CSRF 防护，并配合请求来源校验。使用与会话关联的校验令牌，Ontology 前端从同源接口获取令牌，提交请求时在指定请求头携带，由 Java 校验。校验令牌不作为登录身份或业务权限证明，不进入 URL、日志或 App 包。Cookie 认证下的 POST / PUT / PATCH / DELETE 等方法均需校验，包括语义为查询的 POST、本地登录和退出；读取方法不得承载业务状态修改。配合请求来源 Origin 校验（缺失时采取明确的 Referer 校验或拒绝策略），公开地址从受信部署配置解析，不盲信客户端提供的转发头。嵌入 Workbench 时前端仍运行在 Ontology 来源，不能因父页面在 Workbench 就开放任意跨域读令牌。登录及退出后按框架生命周期重新获取 CSRF 令牌。OIDC/OAuth 协议端点按各自协议的防护单独配置；未来纯 Bearer API 是否豁免须限定在不接受 Cookie 身份的独立认证边界，不能仅因请求有 Authorization 头而绕过。具体接口及兼容版本在实施中确定。

T12：用户确认登录 Cookie 开启 Secure、HttpOnly，限定在 Ontology 主机；跨站内嵌使用 SameSite=None，并保留新窗口使用方式。业务会话 Cookie 不设置 Domain，Path=/；跨站内嵌保持 T11 的 CSRF 与来源校验，仅独立使用的部署可使用 Lax。SameSite=None 不代表 Cookie 可发给任意域名，也不保证浏览器放行第三方 Cookie。按已确认功能规则，浏览器阻止内嵌会话时提供新窗口独立使用入口，不要求用户关闭浏览器安全设置。前端不读取会话编号，也不把编号放入页面 URL 或 App 包。OIDC 登录事务的 Cookie/会话策略与重定向兼容在实施时联合验证，不以此承诺已实现独立的第二套会话。反向代理只信任受控代理链，公网 HTTPS 属性不能由不可信请求头决定。

T13：用户确认以数据库中的项目成员角色为依据，由 Java 业务服务层统一执行权限检查，网页和 Agent 共用规则，数据查询同步限定访问范围。业务服务层统一调用 ProjectAccessService（项目权限服务）判断具体操作能力；Agent 的额外授权范围限制后续单独确认。内部用户身份来自已验证凭证；图谱、节点及关系的真实所属项目由持久化关系解析，不相信前端提交的 user_id、角色或项目归属。数据库中的有效项目成员关系及服务端系统管理员身份为权限事实源，不把角色快照固定在浏览器会话中。列表/统计先在数据库限定授权范围，再分页与汇总；详情/写入解析并校验资源归属，存储操作带授权范围约束，不保留可绕过授权的旧入口。默认拒绝未明确允许的操作，权限不可读取时拒绝受保护访问；系统管理员按已确认的全局业务权限规则显式放行，不等同于数据库超级用户。页面按钮仅展示当前可用操作，不承担安全判断。数据层实现、并发一致性及受控图查询分别深化，不据此确认任意 SQL/Cypher 可用。

T14：用户明确要求保留语句输入查询：在哪个图谱页面输入，就限定在哪个图谱执行；不接受以固定查询类型替代自由输入或默认暂停 Cypher 面板。撤回此前首版关闭自由查询的建议。该产品目标按 T13 在后端落实：根据图谱编号读取真实记录，确认当前用户的项目权限，再由服务器确定实际图库及类型，不相信客户端自报归属或图库名。具体安全执行机制仍须设计和验证，不能把产品目标当作现有接口已安全的证据。2026-10-20 只读复核发现 CypherController.query 仅检查固定 API Key 和图谱存在性，AgeStrategy.query 将传入 Cypher 拼接到 SQL 后执行；本轮未做攻击性验证，不据此声称已证明可跨图攻击。安全改造仍需处理 SQL 文本边界、图谱限定、执行权限及资源限制；不以关键词过滤或拼 WHERE 代替隔离。没有修改业务代码或关闭现有功能。

T15：用户确认语句输入框只用于查询。保留自由输入，并按 T14 限定在当前已授权图谱；所有应用角色（含项目所有者和系统管理员）在该查询入口均不获得语句写入能力。增删改通过业务功能按已确认的项目角色执行。只读要求必须落实到后端执行边界及数据库权限，不能仅靠前端提示、关键词过滤或只读事务提示；具体与 AGE 兼容的强制机制待实现和验收，不声明现有拼接 SQL 的入口已经满足。普通用户可导出有权访问的数据，仍按已确认功能规则执行。

T16：用户确认同一次业务操作涉及的 PostgreSQL 业务表与同库 AGE 写入，由 Java 业务服务层统一管理事务，全部成功才提交，失败则整体回滚。MyBatis 与 JDBC/AGE 需要使用同一数据源、事务管理配置及同一受管连接，不能仅凭添加注解声称已完成。所有权转移等多记录权限变更同样保持整体提交；并发控制机制另行深化。不将一个任意规模的导入或包含外部存储的操作自动视为单事务，本项不确认跨数据库分布式事务。实施时通过真实数据库故障注入验证业务表与图数据无部分写入；现有局部事务测试不能替代完整业务验收。

T17：用户确认 Agent 采用 OAuth2 授权码及 PKCE 获取 Ontology 签发的用户访问令牌，与浏览器登录会话分开管理，共用内部用户及项目权限。区分两条协议链路：Workbench 通过 OIDC 证明网页登录身份；Ontology 作为 OAuth2 授权方，在用户授权后为 Workbench 的工具调用签发关联内部 user_id 的访问令牌。与正式 Calendar App 清单中声明的授权/令牌/用户信息端点和 PKCE 机制对齐；不借用浏览器 Cookie、上游 ID Token 或固定共享 API Key 作为 Agent 的用户身份。令牌只用于已授权接口访问，最终仍受当前项目权限校验，不扩大用户原有权限。由 Java 承接授权及验证逻辑，复用同一内部用户和项目权限服务；沿用已确认身份绑定规则，授权时展示当前 Ontology 账号与申请范围，避免默认为不同账号绑定。敏感凭证由平台的连接与工具运行机制保管/附加，不传给模型正文或 iframe。具体框架版本、令牌格式、scope 划分、有效期、刷新及撤销边界另行确认，并以 Workbench 真实调用验收，正式清单只能证明接入声明。

T18：用户确认 Agent 授权按读取、写入、管理划分，后端同时检查授权范围和当前项目角色，两者都允许才执行。业务范围区分 ontology.read（读取、导出及已授权图谱的只读语句查询）、ontology.write（通过业务接口新增/修改/删除图内容、导入及相应图谱编辑操作）、ontology.manage（项目成员、邀请、所有权和项目删除等管理操作）；profile 仅提供必要账号识别，不赋予业务访问。scope 说明用户委托给 App 的操作类别，项目角色说明该用户对具体资源的实际权限；后端同时验证，两者任一不允许即拒绝。各 scope 作为独立组合明确请求，不隐式以 manage 或 write 获得其他 scope；具体首版组合按 App 声明能力确定，不将默认只读或可任意勾选的 Workbench UI 视为已确认能力。读取/写入/管理映射由 Java 强制执行，系统管理员也受所授 scope 限制，语句输入框仍遵守 T15 只读。授权页面明确展示实际申请范围；增加范围必须重新取得授权，旧 profile-only 令牌不得自动扩权。写入仍按已确认产品规则先确认具体目标和变更范围，该交互确认不能代替服务器权限验证。

T19：用户确认 Ontology 的 Agent 访问令牌采用高强度随机不透明令牌，授权记录保存在 PostgreSQL，令牌本身仅保存单向摘要，由 Java 每次查验。授权信息包括内部用户、客户端、scope、到期时间及撤销状态等；查验后调用统一项目权限服务。授权与接口验证在同一应用时可内部查验，无需为自己增加网络 introspection 调用。访问令牌原值仅在协议响应中交付给受权客户端，不在业务表、日志或 URL 明文保存；密码慢哈希算法不直接套用于高熵随机令牌。OAuth2 组件需适配摘要查找与生命周期，不能假设框架默认存储满足该要求；框架具体版本及实现另确认。此项只选择 Ontology 自己签发的访问令牌，不改变 Workbench 上游 ID Token 的 JWT/JWKS 验证机制；有效期、刷新及撤销范围另行讨论。

T20：用户确认访问令牌单张最长 15 分钟，配发高强度随机刷新令牌，通过轮换自动续期，整体受本次 Ontology 登录验证后 8 小时的固定上限约束。刷新不得滚动延长该截止时间，新访问令牌也不得超出截止时间。刷新时校验客户端绑定、授权有效性、当前账号状态、安全版本及原 scope，不允许扩权；刷新令牌按次轮换，旧令牌作废，保留关联记录用于重用检测，发现作废刷新令牌再次使用时撤销关联授权组。服务端仅持久化刷新令牌摘要。并发刷新串行及超时重试语义须与 Workbench 实际运行机制联调，不能把普通并发直接当作已证明攻击。2026-10-20 核实 Calendar、Base 2、Library 2 正式 manifest 均声明 refreshUrl（与各自 tokenUrl 相同），这证明样例具有刷新配置，尚不证明当前 Workbench 已正确处理本应用的新旧刷新令牌替换。与 Workbench 作为上游 OIDC 签发方是否提供刷新令牌是两件事。网页闲置 30 分钟及 8 小时规则保持不变，后台刷新不延长网页会话；普通退出与 Agent 授权撤销范围下一项讨论。实施完成并通过实际自动刷新、轮换及到期验收后才在新 App 包启用刷新声明。15 分钟/8 小时是本项目已选配置，不是协议规定值。

T21：用户确认普通退出只结束当前网页会话；取消 App 授权收回对应连接；退出全部设备、修改或重置密码、禁用账号统一收回全部旧会话与 Agent 授权。普通退出不延长或重新开始 T20 的授权期限。指定连接撤销对应授权记录及其访问/刷新令牌，不影响其他连接；账号级撤销更新安全版本，重新启用账号不复活旧凭证。移出项目仅取消该项目权限（系统管理员的独立全局权限仍按已确认规则判断）。每次 API 调用和刷新均检查当前授权状态及账号安全版本；撤销与刷新必须在同一授权记录上协调并发，不能生成撤销后仍可用的新凭证。生效边界为撤销提交后进行安全检查的后续请求，不承诺自动取消已执行中的任务。提供标准 OAuth2 撤销接口并保留本地用户主动取消能力，Workbench 的断开连接是否调用该接口需实测；不承诺 Workbench 与 Ontology 的全局退出联动。

T22：用户确认由后端统一保存关键安全和业务审计，区分网页与 Agent 入口，记录必要操作信息并排除敏感凭证。Java 记录登录成功/失败、退出/撤销、账号禁用/密码变更、身份绑定、项目成员与所有权变更、重要业务写入和导入导出、越权拒绝及刷新令牌异常等事件。使用经验证的内部用户与客户端身份，记录时间、调用入口、操作、项目/资源编号、结果及服务端生成的请求关联编号。数据库持久化关键业务审计，成功的关键修改与其成功审计记录在同一事务提交，失败/拒绝事件采用独立受保护日志路径，不能随业务事务回滚消失。记录必要字段及变更概要，不默认记录完整业务正文、完整查询语句或逐条查询结果；批量操作记录范围及数量，避免无界扩张。密码、Cookie、会话编号原值、完整 Token、Secret、授权码及数据库连接凭证不进入日志。应用内审计只追加、按权限查看，无普通业务修改/删除入口；维护清理另走受控流程，不宣称能阻止数据库超级用户篡改。保留期限、可见范围细则、归档清理及失败日志通道故障策略另行确定。

T23：用户确认按账号和可信来源分别限流，连续失败后短期冷却，统一失败提示，避免自动永久锁号或影响已有正常会话。入口层限制异常请求量，Java 按账号及来源地址两个独立维度限制失败尝试，避免仅按 IP 或仅按账号+IP 组合计数。连续失败触发有上限的重试间隔或短期冷却，不因匿名失败自动永久禁用账号、撤销现有会话或封禁另一条已验证的 Workbench 登录路径；拦截期间的请求不无限延长同一次冷却。来源地址仅从受控代理链解析，不能直接信任客户端自报转发头。未验证身份的登录失败采用统一响应，避免暴露账号存在性或禁用状态，并处理明显的响应时间差；限流统一提示尝试过于频繁。相关异常写入 T22 审计且不记录密码。认证、令牌与恢复端点按各自凭证类型限流，正常刷新不与输错密码共用失败计数；业务接口资源限制另行设计。具体阈值、窗口、存储及并发控制在实施时结合当前部署与测试确定，本项不同时确认验证码、MFA 或额外 Redis 服务。

T24：用户确认先在数据库副本完成改造和验收，再保留数据做增量升级，统一切换到 Java 鉴权，并重新登录授权一次。沿用源码已有 Flyway，以新增版本脚本创建身份、会话、成员和授权等结构并补充旧项目归属，不重跑或改写已应用的破坏性初始化脚本。实施前确认实际迁移历史，不仅依据旧文档认定数据库版本。先备份现有完整 PostgreSQL/AGE 数据及必要角色信息，恢复到隔离副本验证，再在副本完成双登录、身份绑定、权限、只读图查询、Agent 授权刷新/撤销及失败回滚验收。按已确认产品规则将旧项目归属到明确指定的初始系统管理员，保留业务编号及图数据；初始管理员与身份映射需在执行前明确，不能取首个登录用户。切换时暂停写入、制作新备份并执行已验证的增量迁移，前端/App 包与 Java 鉴权一并切换；旧 Python 不再发行或验证新凭证，旧会话/令牌失效，用户重新登录连接一次。预先验证恢复方案，不能在新权限版已有写入后直接用旧备份覆盖，也不能回退到公开无权限旧入口。范围仍为本机开发测试环境，不代表授权部署到服务器或现在开始执行迁移。

T25：用户确认使用 Spring 官方授权服务器能力（Spring Authorization Server；新版本整合至 Spring Security），集成到 Ontology 同一 Java 应用中，协议组件与业务权限模块分工。授权组件承接授权码/PKCE、客户端与回调校验、令牌签发/刷新/撤销等标准协议流程；Spring Security 负责通用认证及请求安全，Spring Session JDBC 负责浏览器会话，业务身份及项目权限模块负责内部用户、角色与 scope 映射。OAuth2 组件的扩展与持久化适配实现 T19 的摘要存储、T20 的固定 8 小时截止与刷新重用检测、T21 撤销及 T22 审计；不能将框架特性列表等同于本应用已经满足全部策略。具体版本组合须核对维护状态、当前 Spring Boot 及 MyBatis 等依赖兼容性并锁定；大版本升级单列评估，不在本项默认批准。不开新的独立认证服务，不沿用 Python 自编协议链路；实际 Workbench 联调按正式 App 契约验收。

T26：用户确认两套应用凭证独立管理，分别由对应后端保管，App 通过管理员私密配置接入，公开文件不包含 Secret。区分 Workbench 注册给 Ontology 的上游 OIDC Client ID/Secret，以及 Ontology 注册给 Workbench App 的下游 OAuth2 Client ID/Secret。前者用于 Java 向 Workbench 兑换登录结果，Secret 仅在 Ontology 服务端私有配置或运行环境中保管；后者用于 Workbench 后端向 Ontology 兑换/刷新令牌，原 Secret 交 Workbench 的受保护客户端配置保管，Ontology 授权端保存用于验证的编码值。Client ID 是公开应用标识，Secret 是应用身份凭证，均不替代每个用户自己的访问令牌或项目权限。沿用正式 App 规范中仅供管理员导入的客户端私密配置交付方式，必须核验平台发布后文件可见性，不能把管理端文件约定当成已证明普通用户拿不到；公开 Manifest、成员脚本、前端构建产物及模型上下文不得带 Secret。源码提供占位模板，真实服务端配置不入版本仓库，限制本机文件读取权限且日志脱敏；需要向外请求的 Secret 必须可由对应服务端读取，不能误将上游 Secret 改成无法使用的单向摘要。支持按两条链路独立更换凭证，具体轮换、兼容与交付方式在实施时按 Workbench 契约核验；当前不新增独立密钥管理服务。

T27：用户确认数据库迁移维护账号与 Java 日常运行账号分离，日常账号按最小必要权限运行。迁移/维护账号在受控升级流程执行建表、改表及必要扩展维护；Java 账号仅授予 Ontology 必需的业务表与 AGE 操作权限，不具备 superuser、BYPASSRLS、任意管理数据库/账号等能力，也不能读取迁移维护凭证。已有应用用户与角色继续保存在业务表中，不将应用系统管理员等同数据库超级用户。AGE 的连接加载初始化、运行期图谱创建/删除及图 schema 权限需在实际版本上验证最小授权，必要时在存储适配与受控数据库函数层处理，不因兼容问题恢复全应用超级权限。T15 的自由语句查询采用受限只读执行边界，须同时验证当前图谱访问范围，不能以只读账号等同当前图库隔离。本项确认权限分离原则与验收目标，具体角色/授权 SQL、只读通道及 AGE 兼容机制待工程验证；不在讨论阶段改变现有数据库权限。
